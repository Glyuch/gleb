# Штаб — командный пункт управления командой и фокусами

**Дата:** 2026-08-08
**Статус:** дизайн утверждён Глебом, ждёт план реализации
**Подпроект:** gleb.finance/shtab

## Зачем

Личный инструмент Глеба для ответа на утренний вопрос: **«кто чем занят, покрыты ли мои ключевые фокусы, достаточно ли я сам уделяю им внимания?»** — в виде интерактивной «стратегической карты», где людей перетаскивают между продуктами и проектами, а каждое решение фиксируется с датой.

Единственный пользователь — Глеб (доступ закрыт гейтом по user id). Команда систему не видит. Это не таск-трекер: трекаются фокусы людей, а не задачи.

## Ключевые концепции

- **Территории (objects)** — продукты, проекты, энейблеры. Проект может входить в продукт или быть самостоятельным. У каждой территории — уровень фокуса Глеба: фоновый / 🔥 / 🔥🔥.
- **Персонажи (people)** — сотрудники, включая самого Глеба (он такая же карточка). У каждого класс-роль (аналитик, маркетолог, разраб, биздев…), цвет, признак прямой/непрямой, руководитель.
- **Назначения (assignments)** — «кто на какой территории, в какой роли, с какого числа, почему». Снятие не удаляет запись, а закрывает её датой — копится история.
- **Метрики-флажки (metrics)** — название + статус 🟢🟡🔴 + текстовое значение, вручную. Привязаны к продукту или к бизнесу в целом. Источник правды — внешние дашборды; здесь только проекция на решения о людях.
- **Хроника (events)** — автоматическая лента всех действий: назначил, снял, сменил статус метрики, сменил уровень фокуса. С комментариями Глеба «почему».

Выводимое, не хранимое: дыры покрытия (🔥-территория без активных назначений + сколько дней), перегрузы (у человека слишком много активных 🔥-назначений), «работают вместе» (общие активные назначения), «без фокуса» (человек без единого назначения).

## Модель данных

Общая MySQL-база gleb.finance, префикс таблиц `shtab_`.

```
shtab_people
  id, name, initials, class (string), color, is_direct (bool),
  manager_id (nullable → shtab_people), is_me (bool), sort,
  archived_at (nullable), timestamps

shtab_objects
  id, type ENUM(product|project|enabler), parent_id (nullable → shtab_objects),
  name, emoji, focus_level TINYINT (0 фоновый | 1 🔥 | 2 🔥🔥), color, sort,
  archived_at (nullable), timestamps

shtab_assignments
  id, person_id → shtab_people, object_id → shtab_objects,
  role_label (string), comment (nullable text),
  started_at (date), ended_at (nullable date), timestamps
  -- активное назначение: ended_at IS NULL

shtab_metrics
  id, object_id (nullable → shtab_objects; NULL = бизнес в целом),
  name, status ENUM(green|yellow|red), value_text (nullable), sort, timestamps

shtab_events
  id, type (string: assignment_started | assignment_ended |
      metric_status_changed | focus_level_changed | object_created |
      object_archived | person_created | person_archived),
  person_id (nullable), object_id (nullable), metric_id (nullable),
  payload JSON (старое/новое значение и т.п.), comment (nullable),
  created_at
```

Правило целостности: каждая мутация пишет событие в `shtab_events` в той же транзакции.

## Визуальная идентичность

Утверждена по мокапам (финальный: `docs/superpowers/specs/assets/2026-08-08-shtab-cockpit-final.html`).

- **Не** копия Miro: без дот-грида и свободных стикеров. Язык — «штаб кампании».
- Светлая тёплая палитра «бумажной карты» (#F2F0EA фон), сектора-территории с цветными границами и лёгкой заливкой цвета сектора, непокрытые — янтарный/серый пунктир.
- Карточка-персонаж (структура «персоны»): медальон-аватар с кольцом цвета класса, имя, чип класса, стат-плитки (фокусы / из них 🔥), строка «на секторе с 12.07». Развёрнутая карточка (таб «Люди» / клик): + загрузка, руководитель, «работает с», личная хроника.
- Игровая механика без игровой графики: перетаскивание персонажей, гемы-статы, пустые слоты «+» на непокрытых территориях.

## Экран и взаимодействия

Один SPA-экран, три таба: **Карта · Люди · Хроника**. Верхняя панель: табы + Резерв (люди без назначений).

**Карта (главный, открывается по умолчанию):**
- Сектора в CSS-grid: продукты (🔥🔥 первыми), их проекты прижаты к родителю, самостоятельные проекты/энейблеры отдельно. Позиции не хранятся — автолейаут.
- В секторе: заголовок с 🔥-уровнем, точки метрик, карточки-персонажи, пустой слот «+» если территория без людей (с «пусто N дней» для 🔥-территорий).
- Справа панель Хроники (последние события, фильтры-ссылки).
- Назначение: drag персонажа (из резерва или другого сектора) на сектор → мини-диалог «роль + комментарий» → запись. На таче/мобиле — тап по «+» → пикер человека.
  Drag между секторами = снять там, назначить здесь (два события, один диалог).
- Снятие: меню на карточке → «снять с территории» + комментарий.
- Клик по точке метрики → поповер: статус 🟢🟡🔴 + значение + комментарий.

**Люди:** крупные карточки, группировка «прямые / непрямые», у каждого полный список фокусов с датами; подсветка «без фокуса»; клик — личная хроника.

**Хроника:** полная лента, фильтры: все / назначения / метрики / по человеку / по территории.

**CRUD:** модалки для людей, территорий, метрик. Первичное заполнение — вручную через эти же модалки.

## Архитектура

По правилам монорепы (AGENTS.md): работа на сервере, ветка master, `npm run build`.

- **Маршруты:** `/shtab` (страница) + `/shtab/api/*`. Гейт: только user id Глеба, 404 остальным.
- **Бэкенд:** Laravel — миграции, Eloquent-модели, тонкие контроллеры, FormRequest-валидация.
  - `GET /shtab/api/board` — весь стейт одним ответом: люди, территории, активные назначения, метрики + посчитанные флаги (дыры с количеством дней, перегрузы, резерв, «дней на объекте»). Масштаб (~13 людей, ~20 территорий) позволяет без кэшей и пагинации.
  - Мутации: `POST assignments`, `POST assignments/{id}/end`, `PATCH metrics/{id}/status`, `PATCH objects/{id}/focus`, CRUD `people|objects|metrics`. Всё пишет events транзакционно.
  - `GET /shtab/api/events` — лента с фильтрами, пагинация страницами.
- **Фронтенд:** React-экран в общем фронте репы; drag-and-drop — dnd-kit либо уже используемая в репе библиотека (решается на этапе плана). После мутации — refetch board, без оптимистичного стейта.
- Порог перегруза: константа конфига (по умолчанию: >2 активных 🔥-назначений), не UI-настройка.

## Ошибки

Валидация на бэке (FormRequest), фронт показывает ошибки тостами. Конфликтов конкурентного редактирования нет (один пользователь). Битые ссылки (архивный человек в активном назначении) запрещены на уровне валидации: архивировать человека/территорию можно только после снятия активных назначений (UI предлагает снять разом с одним комментарием).

## Тестирование

- Laravel feature-тесты: жизненный цикл назначения (создать → снять → история сохранилась), запись событий на каждую мутацию, расчёт дыр/перегрузов/резерва в board, гейт доступа (чужой user → 404).
- **Перед прогоном тестов обязательно `php artisan config:clear`** — известные грабли: закэшированный конфиг направляет тесты в продовую базу.
- Фронт в v1 — ручная проверка (десктоп + телефон, read-only сценарий и назначение через пикер).

## Не входит в v1

Вид «нити» (люди↔фокусы), группировка карты по веткам подчинённости, история значений метрик и графики, дайджесты/напоминания, тёмная тема, экспорт, мобильный drag (если dnd-kit не даст бесплатно), доступ команды (роли/read-only), интеграции с внешней аналитикой. Модель данных всё это допускает без переделок.

## Критерий успеха

Через две недели после запуска: в штабе реальная команда Глеба; сделано ≥1 настоящее перераспределение через интерфейс; на вопрос «когда я поставил X на Y и почему» отвечает Хроника.
